## 実装における計画と反省

### 全体を通じた設計思想

大きくまとめると次の3点を意識した

* 基本的に、PyTorchライクの入出力形式を目指した。
* オブジェクト指向的な書き方を意識し、SOLID原則に基づいたコーディングを目指した。
* 重要な箇所ではPythonの型注釈を最大限意識した。
    * できるだけNoneを許さないように書いたが、それが仇となった部分もある。

### レイヤーについて

#### 抽象レイヤーについて

まず抽象レイヤーを定義しようと試みた。
抽象レイヤーはパラメータを含まないものと、そこから派生させたパラメータを含むものに分け、それぞれの共通処理と抽象メソッドに関する契約を記す計画だった。

パラメータなしレイヤーなら
* 共通処理
    * 学習モード・推論モード切り替え
* 抽象メソッド
    * 順伝播
    * 逆伝播

パラメータありレイヤーなら以上に加えて
* 共通処理
    * パラメータ初期化メソッド
    * パラメータ取得メソッド
* 抽象メソッド
    * パラメータ初期化に際して必要な情報を取得するメソッド(プロパティ)

などとして定義しようと考えた。このように考えた理由は、パラメータ初期化処理を抽象レイヤー側にまとめることで、コードの繰り返しを避けるとともに、各レイヤーでメソッドの入出力に関する契約を固定し、共通した処理をとして扱えるようにするためである。

この方針に従って、[`src/neural_networks/layers/abstract_layers.py`](../../src/neural_networks/layers/abstract_layers.py)を実装した。

この設計における最大の反省点は、バッチ正規化層の存在を考慮していなかった点にある。ParametricLayerクラスは、誤差逆伝播法によって更新されるパラメータを持つレイヤーの基底クラスであると考えて実装していた。そしてそれは今回の実装範囲ではLinearとConv2Dのみであると考えていた。これら2つはいずれもStandard / Xavier / He の初期化によって初期化される重み行列と、全てゼロによって初期化されるバイアスベクトルからなり、従ってそのようなレイヤーをParametricLayerとして抽象化しようと実装した。

なので当初は

1. 更新対象パラメータなし -> Layerを継承
2. 更新対象パラメータあり = 重み行列Wとバイアスベクトルbを持つ -> ParametricLayerを継承

と考えていて、パラメータ更新に関するメソッドもParametricLayerにのみ入れていた。

しかしバッチ正規化層の実装をするときに、重み行列 + バイアスベクトルではない更新対象パラメータがあることに気づいた。ParametricLayerをより抽象化することも考えたが、その時にはすでに大部分の実装を完了してしまっていて、最終的にLayerを変更するに至った。結果としてLayerの設計が汚くなてしまったことが反省点である。

1. パラメータなし
2. パラメータありだが、重み or バイアスではない(初期化メソッドが不要)
3. パラメータありで、重み or バイアスである(初期化メソッドが必要)

の3段階に分けるべきだった。

一方でこの設計の利点もいくつかある。最も良かったのは、Sequentialの実装が簡単になったことである。各Layerの情報はLayerのリストとして持っておいて、Sequential自身のメソッドは、その中身の各レイヤーのメソッドを順番に呼び出すだけで済んだので、とても簡単に実装できた。

#### CNN系レイヤーについて

今回最も難しかったのが、CNN系レイヤーにおけるpaddingである。

[`src/neural_networks/layers/convolutional_layers.py](../../src/neural_networks/layers/convolutional_layers.py)に書かれている。

順伝播は簡単だったのだが、padding modeで"Zeros"以外を選んだ時の逆伝播の実装が難しかった。単にPaddingを切り捨てていたが、それでは次の点で不十分だった
* "Symmetric" / "Edge" / "Reflect"を選択した場合、paddingされる値は実際の入力値に依存するので、逆伝播時の勾配計算にも関係してくる
* "Zeros"の場合のみ、Paddingが0 = 勾配が0 = 切り捨てていい なので成立するが、それ以外では誤った勾配計算がなされる。

これを修正するために、padding_backward関数を実装し、paddingによって勾配がどのように逆伝播するかを算出してから逆伝播するように実装した。

ただしこれもオブジェクト指向的に考えればあんまり綺麗ではない。

#### Sequential層について

Sequential層の実装にあたっては、まずこのようなレイヤーをまとめる役割を、レイヤーとして実装するか、別で`Model`のようなクラスを定義して実装するかで迷った。

ただ`Model`のメソッドを考えてみると、ほぼ全て`Layer`と一致したので、Layerから派生させて作ろうとなった。これによってSequentialのSequentialなども可能になるので、使い勝手もいいと考えた。この時点で、`model = Sequential(...)`としてモデルを定義する方向性が確定した。

実装にあたっては、前述した通りオブジェクト指向的に抽象レイヤーから派生させていったのが効き、簡単に実装できた。

また個人的には、trainプロパティの更新をうまく書けたと思っている。setter / getterをうまく使って、単に`sequential.train = True / False`と代入のように書くだけで、内部のレイヤーのモードを変更できるように実装できた。

### 最適化器について

[`src/neural_networks/optimizers/optimizers.py`](../../src/neural_networks/optimizers/optimizers.py)に実装した。

まず悩んだのは、モデル(=Layer)からどのようにして更新対象のパラメータをもらうかという点である。

ParametricLayerにだけ自身の重み行列とバイアスベクトルを返すメソッドを実装すればいいと考えたが、以下の点で不適であることがわかった。
* バッチ正規化層を考慮できていない
* 重み行列とバイアスベクトルを直接プロパティ化すると、NumPyの仕様上、再代入時に参照が切れてしまい、不正な状態の値を参照してしまう。

そこで、最適化器はレイヤーオブジェクトへの参照と、レイヤー内においてパラメータを保持しているプロパティの名前を保持し、最適化器 -> レイヤー -> プロパティと2段階の接続によってパラメータを参照するようにした。より具体的には、最適化器は(レイヤー、パラメータのプロパティ名、対応する勾配のプロパティ名)のタプルとしてそれぞれの更新対象のパラメータを保持する。これらタプルはリストとしてまとめて保持される。

そのために、まずLayerにget_paramsメソッドを導入した。この時点では空のリストを返すメソッドである。そして更新対象のパラメータが存在するレイヤーは、このメソッドをオーバーライドし、自身が保有するパラメータのタプルのリストを返却するメソッドとして再定義する。

これによって、先ほど述べた2つの問題を解決した。

## 実装において得た学び

### 線形代数の理解が足りない

実装したり、途中計算を追っていたりしていて、線形代数の理解が足りていないことを何度も痛感した。ベクトルや行列が関係する微分をはじめとして、今一度線形代数を学び直そうと思った。

### 各種初期化の詳細と理由

一度学んだことだったが、改めて理解することができた。特に後に続く活性化関数によって Xavier / He のどちらで初期化するべきか変わるというのが統計的に理解できた。

### バッチ正規化層の詳細

Kaggleや論文を読んでいると必ずと言っていいほど登場するバッチ正規化層について、その詳細を理解することができた。なんとなく単に「正規化する」の漠然とした理解だったが、学習 / 推論の両方でどのような挙動をするのか、パラメータはどのように更新されるのかがとてもよくわかった。

### テスト作成の困難さ

テストの作成は方針を変更し、AIに作成させた。この理由は想像していたよりテストの作成が困難だったことにある。特にレイヤーのパラメータがランダムで決定されるので、決定論的なテストの作成が困難であった。これは多数の要素が絡み合う上流のコンポーネントのテストほど顕著であった。テスト作成にあたってのノウハウは技術書などで学びたいと思った。

### 設計の難しさ

Layer / ParametricLayerをはじめとして、抽象クラスを定義してから具体的なコンポーネントを実装していった。どのような引数でインスタンス化するか、共有する / 各自で実装するメソッドの判断はどうするかなど、考えることが多かった。またバッチ正規化層の件では、設計時に想定していなかった事項によって設計が大幅に汚くなるという問題を実際問題として強く感じることができた。最近はほぼ全てのコードをAIに書かせているが、その中でも継ぎ足しのコードではなく、拡張性・保守性に優れたコードを書くことが重要であると再確認できた。
